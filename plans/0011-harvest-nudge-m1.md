# Plan: Harvest from the nudge Milestone 1 session — two global rules, two stack-note entries, one skill fix

## Goal

The nudge session of 2026-09-22 to 2026-09-24 built and accepted a Cloudflare Worker end to end. Five of its lessons generalise beyond that repository and would otherwise be rediscovered at a cost: one near-miss on production, about thirty minutes of hung installs, one premature review report, and one correction from the user about how shared guidance may change.

## Changes

- `CLAUDE.md` § Continuous Learning — captures that change shared guidance are additive while projects still follow the old guidance.
- `CLAUDE.md` § Debugging — never trim *undocumented* warning or error lines out of a command's output, above all for dry runs and deploys; a diagnostic already written down as benign may be filtered, and the exit status must survive either way.
- `docs/typescript.md` — new § Cloudflare Workers deployment (environments inherit custom-domain routes; `routes = []` pinned by a test) and § Bun install and tooling traps (the install-cache hang; no `timeout` on macOS).
- `docs/rust.md` § Testing & test harness — the expected-warning baseline no longer recommends `cargo check 2>&1 | grep "^error"`. That command contradicted the new § Debugging rule and was independently broken: it reports grep's exit status, so a failing build exits 0 and a clean build exits 1. Added by the round-2 review; **this file was not in the PR's original scope**.
- `skills/codex-review/SKILL.md` step 2 — wait for a standalone verdict line or process exit, never the bare phrase; the matcher tolerates quotes, surrounding space, `**bold**` and CR, and an exit with no matching verdict is reported as inconclusive.

- **Codex review, 2026-09-24** — run per `/codex-review` on the branch diff; verdict `CODEX VERDICT: CHANGES REQUESTED`, seven findings (two HIGH, three MED, two LOW). Five accepted and fixed here. The one that mattered: the § Debugging rule as first written contradicted two standing rules — `docs/rust.md` § Testing & test harness *prescribes* `cargo check 2>&1 | grep "^error"`, and `plans/0006` § Separately blesses filtering `failed to store: 100001`. A stack-note entry is a rule per § Stack Notes, so the harness would have shipped holding both sides of a contradiction; the rule now turns on whether the diagnostic is *documented*. Also accepted: the file-count error above, the `timeout` overstatement, treating a verdict-less exit as inconclusive, and a carve-out so the additive rule cannot freeze guidance that is simply wrong.
- **Severity disagreement, recorded rather than argued** — Codex rated the verdict-matcher false negative HIGH. Downgraded to LOW and fixed anyway. The bug this PR set out to kill made the wait end *too early*; a missed match makes it end *late*, at process exit, which is the safe direction, and the review that produced this finding was itself matched by the bare pattern. Hardening it costs nothing, so the disagreement is about severity only — noted here so the next reviewer does not re-litigate it from scratch.
- **Codex review round 2, 2026-09-24** — verdict `CODEX VERDICT: CHANGES REQUESTED` again, and it was right to: the round-1 fix had *cited* `docs/rust.md`'s `grep "^error"` baseline as an example of permitted filtering, when that command does not qualify under the very rule being written — it drops unclassified warnings wholesale. Citing as exemplary something the rule forbids is a worse defect than the original contradiction, because it reads as settled. Resolved by correcting `docs/rust.md` at source and citing only the one qualifying example (`plans/0006`). Round 2 also caught that the correction carve-out, as first worded, commanded an immediate edit and so contradicted § General and this section's own confirm-first requirement; it now says *propose*.
- **Scope widened deliberately, once** — `docs/rust.md` was outside this harvest's scope. It was edited anyway because the alternative was shipping a harness that holds both sides of a contradiction, and because the command was independently broken in a way that reports a failing build as success. Flagged in the Changes list so it can be dropped from the PR if that call is not wanted.
- **Codex review round 3, 2026-09-24** — `CODEX VERDICT: CHANGES REQUESTED`. Round 2's fix to `docs/rust.md` was itself broken under zsh: it assigned `status=$?`, and `status` is read-only there. Two rounds in a row, the fix for a zsh trap introduced the next one — which is the argument for running a snippet before documenting it, not for reasoning harder about it. The snippet in the note is now executed output, in both shells. Round 3 also confirmed the carve-out fix closed and found **no other** non-compliant output filter in `docs/` or `skills/`, which was the generalisation check: the rule catches a class, and the class has one member.
- **Partially rejected** — Codex called the additive-guidance rule “too absolute” at MEDIUM, arguing it forces proven-unsafe guidance to persist. The rule already said *while existing projects still follow the current guidance* and *replace the old one only once nothing depends on it*, which covers the ordinary case; the gap was only that it never said corrections are exempt. One clause added, severity not accepted.

## Verification

- `git diff master --name-only` touches exactly **five** files: `CLAUDE.md` (two sections), `docs/rust.md`, `docs/typescript.md`, `skills/codex-review/SKILL.md`, and this plan. (Count files, not bullets: the Changes list has five bullets and two of them are `CLAUDE.md`. The original wording “the four files above plus this plan” made exactly that mistake and implied five when the answer was four; it is five now only because round 2 added `docs/rust.md`.)
- The codex-review `grep` pattern was tested **in both directions** on 2026-09-24, nine cases, all passing: it matches a standalone verdict bare, single-quoted, `**bold**`, CR-terminated, and with leading or trailing space; it does not match the echoed prompt line `'CODEX VERDICT: LGTM' or 'CODEX VERDICT: CHANGES REQUESTED'.` nor the phrase embedded in prose. The original check ran one direction only (the echo), which is why it did not notice that the strictly-anchored form rejected a genuine verdict the prompt itself displays in quotes.
- The inverted exit status of `… | grep "^error"` was measured, not reasoned: a simulated failing build (`error[E0382]…`) exits **0** through the pipe and a simulated clean build exits **1**. This is why `docs/rust.md` was corrected rather than cited as a precedent.
- Two zsh traps found by measurement while fixing `docs/rust.md`, each one introduced by the previous attempt at the fix. `${PIPESTATUS[0]}` is unusable under zsh (after `false | true`: bash `PIPESTATUS=(1 0)`, zsh `PIPESTATUS=()` with the value in `pipestatus`, 1-indexed) — so the guidance redirects rather than pipes. Then `status=$?` turned out to abort under zsh, where `status` is a read-only alias for `$?` (`zsh:1: read-only variable: status`) — so the variable is `rc`. The snippet was then extracted **from the file as written** and run against a stub cargo in both shells — three cases: clean build → nothing shown, exit 0; broken build → only `error[E0382]`, exit 101 (cargo's status, not grep's); and clean build plus one *new, unbaselined* warning → that warning shown, exit 0. The third case is the one that proves compliance with § Debugging: the filter suppresses only what the baseline names and cannot hide an unclassified line.
- `Bun.TOML.parse` confirmed present on bun 1.3.5 — the version the note cites — and parsing `[env.<name>]` with `routes = []` as described.
