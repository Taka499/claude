# claude — central Claude Code configuration

This repository **is** the live user-level Claude Code configuration (`~/.claude`) for this machine, versioned and developed like software. Merging a PR here changes the harness for every project.

The approach emulates [isamu/claude](https://github.com/isamu/claude) (see the article [「コードレビューをやめた」](https://zenn.dev/singularity/articles/stopped-reviewing-my-code)): the global config lives in a repo, every change is a PR, and the PR history records how the harness evolved. The content, however, follows this user's own system — ExecPlans as immutable narrative logs, ADRs with a three-gate filter and mandatory provenance, and `CLAUDE.md` as an auditable index — originally developed in `Taka499/project-template` and battle-tested in `gakumas-rehearsal-automation`.

## Layout

- `CLAUDE.md` — the global rules file, deployed as `~/.claude/CLAUDE.md`. Thin by design: always-on rules only; long reference material lives in `docs/` and is read on demand.
- `skills/` — user-level skills, linked individually into `~/.claude/skills/` (which stays a real directory shared with other tools' skills, per ADR 0003). General-purpose only; project-specific skills stay in their repos. Only `grill-me` sets `disable-model-invocation: true`, and deliberately: it opens an open-ended interview that must never start on its own inference. The rest (`close-out`, `harvest-session`, `codebase-design`, `adopt-from-sibling`, `backlog`, `codex-review`, `scaffold-project`, `explainer`, `task-board`) are safe for the model to reach for when the situation matches their description.
  - **`scaffold-project`** asks, as a separate yes/no against the full target path, whether to create the directory at all before touching the filesystem. It never commits, creates the GitHub repository or pushes without a separate go for each.
  - **`task-board`** changes a board only through its helper `skills/task-board/board.py`, and only in a project that has a `.task-board.json`. Its rules keep a session to queued work and to the issues it files or claims (`plans/0030-issues-workflow.md`). Tests: `python3 -m unittest discover -s skills/task-board`.
- `commands/` — user-level slash commands, deployed as `~/.claude/commands/`. Short prompt templates (`/execplan`, `/commit`, `/read-docs`); anything with real procedure belongs in `skills/` instead.
- `git-hooks/` — branch protection for the user's repositories. `reference-transaction` is git's own hook: it refuses any update of `main`, `master` or `develop` made through git that is not a merge, whatever command or program runs git; creating one passes. It acts only where some remote's fetch or push URL is on `github.com` with the owner `Taka499` or `tia-tools` (parsed from the URL, not matched anywhere in it), or where there is no remote, so clones of other people's projects still pull; a fork the user owns is protected, so syncing upstream into it takes a merge.
  - `install-global.sh` copies it to `~/.config/git/protect-branches` and defines it in `~/.gitconfig` as a config-defined hook, once per machine; every repository is then covered, and each repository's own `.git/hooks` (Git LFS) keeps running. It needs a git that runs config-defined hooks: Homebrew's 2.56 does, Apple's `/usr/bin/git` 2.50 does not. Before reporting success it confirms the configured command is its unchanged copy and enabled, and that a scratch commit on `develop` is refused with the hook's own message, the probe's commits ignoring the machine's signing and commit hooks; `--check` runs only that proof. Run it outside the sandbox.
  - `protect-branches.sh [REPOSITORY]` is the per-repository fallback for a machine whose git ignores config-defined hooks.
  - The hook cannot stop `core.hooksPath` or a `hook.*` setting given for a command (the user's bypass, which a script can use as well), or a process writing ref files directly instead of running git; plan 0019 § Decision Log has both.
  - `protect-github.sh OWNER/REPOSITORY` creates or updates a GitHub ruleset blocking deletion and force pushes of those branches; the free plans enforce it on public repositories only.
  - Tests: `python3 -m unittest discover -s git-hooks`.
- `docs/` — read-on-demand references: the canonical ExecPlan methodology (`PLANS.md`), distilled stack notes (`rust.md`, `typescript.md`, `python.md`, `github-actions.md`, `cloudflare.md`, and `claude-code.md` for Claude Code itself), the cross-stack testing doctrine (`testing.md`), and this repo's ADRs (`docs/adr/`).
- `plans/` — lightweight plan files (goal / changes / verification) committed alongside non-trivial PRs. Not full ExecPlans: harness changes are small and reversible, so the ceremony is scaled down deliberately (see `plans/0001-bootstrap-central-claude.md` § Decision Log).

## Deployment

Clone anywhere, then symlink the tracked pieces into `~/.claude` (the rest of `~/.claude` — sessions, todos, settings — is runtime state and stays untouched):

    ./setup.sh              # macOS / Linux / WSL / Git Bash
    pwsh ./setup.ps1        # Windows PowerShell (uses junctions for dirs; may need Developer Mode for the file symlink)

Both scripts are idempotent and back up anything pre-existing before linking. Note what that means for a *directory*: `~/.claude/commands` is replaced wholesale, so anything previously living there leaves the live config and survives only inside the timestamped `commands.pre-central.*` backup. The scripts print a warning when this happens — port anything you still want into this repo and re-run. After deployment, the working tree of this clone is live config: keep it on `master` except while developing a change.

`skills/` is the exception, and deliberately: `~/.claude/skills` stays a **real directory** into which this repo links one skill at a time, because it is a shared namespace other tools install into — see [`docs/adr/0003-skills-are-linked-per-skill.md`](docs/adr/0003-skills-are-linked-per-skill.md). Two things follow. Adding or renaming a skill takes a `./setup.sh` re-run before it is live, unlike editing an existing one, which is live immediately. And a skill removed from the repo, or absent on the branch you just checked out, leaves a dangling link that the next run prunes — pruning only ever touches links pointing into this repo, never a real directory another tool put there.

### Git in this clone needs the sandbox turned off

Claude Code hard-protects agent-configuration paths from writes by sandboxed commands, and resolves symlinks when it does. Since this repo *is* that configuration, `CLAUDE.md` and `commands/` are **not writable by sandboxed Bash** here — including git's own writes. A `git checkout` that needs to rewrite them fails halfway and can truncate other files: one did exactly that after the PR #2 merge, leaving `docs/PLANS.md` at zero bytes.

So: **git operations touching `CLAUDE.md` or `commands/` must run outside the sandbox** (`dangerouslyDisableSandbox`), which covers `checkout`, `switch`, `merge`, `pull`, `stash` and `restore`. **`.git/config` is protected on the same footing**, which adds a second trigger with nothing to do with the working tree: `branch -d`, `branch -m`, `remote`, `config` itself — anything that rewrites the tracking sections. That one fails *partially* and reports success, so it is the easier of the two to miss: a sandboxed `git branch -d` deletes the ref, fails to drop the matching `[branch "…"]` section with `could not lock config file .git/config`, and exits saying `Deleted branch`. Stale config accumulates behind an apparently clean run — check with `git config --get-regexp '^branch\.'` after any sandboxed branch surgery. Work confined to `docs/`, `plans/`, `skills/`, `README.md` or the setup scripts is fine sandboxed. No `settings.json` change lifts either constraint; `allowWrite` and `excludedCommands` were both tried and re-tested after a restart. Details, evidence and the mid-failure recovery procedure: [`plans/0006-sandbox-vs-agent-config-paths.md`](plans/0006-sandbox-vs-agent-config-paths.md).

`gh` also has to run outside the sandbox, unless a project gives it a token of its own, for two reasons unrelated to the git ones. It is a Go binary, and Go on macOS verifies TLS certificates through the `com.apple.trustd.agent` service, which the sandbox blocks: every call fails with `x509: OSStatus -26276`. Unlike the git constraints above, that part can be lifted, in two ways:
- `SSL_CERT_FILE=/etc/ssl/cert.pem` makes Go check against the certificate file macOS ships, without trustd. A project that opts in sets it beside its token, and only there (the `SSL_CERT_FILE` bullet in § The one file this repo does not deploy). Measured on 2026-10-28 with gh 2.103.0: `gh api` got an answer from GitHub inside the sandbox with it, and failed on TLS without it.
- `sandbox.enableWeakerNetworkIsolation` stays off, because it opens trustd as an outbound channel the domain allowlist does not cover.

The token is the other reason. Since the `~/Library/Keychains` deny (§ The one file this repo does not deploy), `gh` cannot read the user's login inside the sandbox: `gh auth token` fails with `no oauth token found for github.com`, as measured in plan 0016 right after the deny went in and again on 2026-10-09. That deny stays. A project that needs `gh` sandboxed, for issues as its task store say, points `gh` at a narrow token of its own instead (the per-project token bullet in that section). The global `CLAUDE.md` § Git Operations carries the working rule. [`plans/0016-gh-sandbox-tls.md`](plans/0016-gh-sandbox-tls.md) and [`plans/0027-gh-sandboxed-per-project.md`](plans/0027-gh-sandboxed-per-project.md) have the evidence and the decisions.

Note the accident of good fortune in ADR 0003, and its limit. Because `~/.claude/skills` is no longer a symlink to `skills/`, this repository's own `skills/` directory is not a resolved agent-config path and stays writable — linking per skill removed a breakage nobody had noticed yet. But `~/.claude/skills` *itself* is protected: creating a link inside it from sandboxed Bash fails with `Operation not permitted`. So **`./setup.sh` needs the sandbox off whenever it has a link to add or prune**; on a run where every link already exists it succeeds sandboxed, which is why the constraint stayed invisible until a skill was added.

### The one file this repo does not deploy

`~/.claude/settings.json` stays untracked and hand-maintained, per [`docs/adr/0002-settings-json-stays-untracked.md`](docs/adr/0002-settings-json-stays-untracked.md): Claude Code owns that file and rewrites it at runtime, and there is no user-level local-override tier to split app-written preferences from hand-authored policy. The trade-off is that `permissions` — where the git rules are actually *enforced* — is unversioned, so the invariants live here instead and are worth re-checking whenever the file is touched:

- No history-mutating git command (`commit`, `push`, `merge`, `rebase`, `reset`) may sit in `permissions.allow`, so the harness enforces `CLAUDE.md` § Git Operations rather than relying on the agent obeying prose. A stale `Bash(git commit *)` allow entry contradicted that rule undetected until an audit found it. Since 2026-10-12 neither `git commit` nor `git merge` sits in `ask`: approving a task is standing permission to commit on its feature branch, and a rule matching command text cannot tell that branch from `develop`, so an `ask` rule for either would prompt for every feature-branch commit or merge again. `git push` stays in `ask`; `rebase` and `reset` stay denied. Evidence and decision: [`plans/0018-commit-approval-ladder.md`](plans/0018-commit-approval-ladder.md); why no hook asks on the protected branches instead: the next bullet.
- **No `hooks.PreToolUse` entry runs code from this clone.** Until 2026-10-28 one ran `hooks/git_gate.py` on every Bash call, to ask before history landed on `main`, `master` or `develop`. It ran outside the sandbox from a file every session could write, since `allowWrite` opens this clone to all of them, so one sandboxed write became code run unsandboxed in every session. It also prompted about 225 times in 16 days, about 164 of them for commands it could not read. A hook added here again must follow [`docs/claude-code.md`](docs/claude-code.md) § Code that runs outside the sandbox. In its place:
  - git's own `reference-transaction` hook refuses every update of those branches that is not a merge, creating one excepted (§ Layout, `git-hooks/`);
  - `permissions.ask` holds `Bash(git -c *)`, `Bash(git --config-env*)` and `Bash(/usr/bin/git *)`, the plain forms that switch git's hook off for one command or run a git that ignores it;
  - it also holds `Bash(git branch -d*)`, `-f*`, `-m*`, `-M*`, `-C*`, `--delete*`, `--force*` and `--move*` beside the older `-D`, because `allow` holds `Bash(git branch *)`;
  - and `Bash(git update-ref *)`, `Bash(git switch -C*)`, `Bash(git filter-branch *)`, `Bash(git filter-repo *)` and `Bash(git replace *)`, which rewrite a branch the way the denied `reset` and `rebase` do;
  - a push asks twice over: `Bash(git push *)` is in `ask`, and it runs outside the sandbox, as `gh pr merge` does, where `Bash(dangerouslyDisableSandbox:true)` asks;
  - in auto mode, the classifier's `soft_deny` names protected-branch history and pushes (next bullet).

  Left open, knowingly:
  - a merge into a protected branch prompts only in auto mode: an `ask` rule for `git merge` would also prompt for merging the integration branch into a feature branch, which is standing permission;
  - creating `main`, `master` or `develop` (`git branch develop <start>`, `git switch -c main`), which git's hook allows: a rule could not tell it from `git switch develop` making the local branch from `origin/develop`, and a branch made that way reaches GitHub only by a push, which asks;
  - `git switch -f` and `--discard-changes`, which drop working-tree changes the way `git restore` does, and nothing asks for `restore` either; in auto mode the classifier judges both;
  - `git -C <repo> branch -d …`, which `allow Bash(git -C * branch*)` passes;
  - `git worktree add -B` and `git worktree remove --force`, and a `fetch` with a `+` refspec into a local branch, since a rule on either command would prompt for its routine use;
  - every form a text rule cannot see: `bash -c`, `GIT_CONFIG_*` variables, a script that runs git.

  Evidence and decision: [`plans/0025-remove-git-gate.md`](plans/0025-remove-git-gate.md).
- **`hooks.PermissionRequest` holds one logger, written inline, run with `"async": true`, and printing nothing.** Each time Claude Code is about to ask for permission, the entry appends one JSON line to `~/.claude/permission-requests.jsonl`, using `/opt/homebrew/bin/jq`:
  - UTC time, session id, subagent id, folder, permission mode and tool name;
  - the first 200 characters of the command, file path or URL.

  No session log records these requests, so this is the only count of the approvals the user is asked for.
  - **Why `PermissionRequest`:** a `Notification` hook on `permission_prompt` fires only after a dialog has waited about six seconds, so quick approvals would go uncounted.
  - **It counts requests, not exactly dialogs shown.**
    - The event also fires where a call that can't prompt would be auto-denied, such as a background subagent or a non-interactive run.
    - `AskUserQuestion` logs a line too, as `tool: "AskUserQuestion"`.
    - A call that auto mode lets through with no dialog logs nothing.

    Measured on 2026-10-28, except the auto-denial case, which is from the docs. A review counts approval dialogs by filtering on the logged fields, and checks doubtful lines against the transcript.
  - **Keep it async and silent.** Per the docs, an async hook's decision fields have no effect, and Claude Code doesn't wait for it, so it can neither decide nor delay a dialog. Run synchronously, a decision object on stdout would allow or deny the call, and a hung `jq` would delay the dialog. Its stdout goes to the log in any case.
  - **The one hook allowed to write,** and only to its own log. It is an inline command in this file, which no session can write, so there is no script to protect.
  - **Its log is safe from sessions:** they cannot write `~/.claude` itself.

  The exact entry and its tests: [`plans/0028-permission-request-log.md`](plans/0028-permission-request-log.md).
- **`autoMode` must agree with the commit rule two bullets up, because the classifier enforces its own copy.** `/auto-mode-setup` once wrote a `soft_deny` entry blocking every `git commit` "without explicit per-operation permission"; left in place, it would have kept refusing feature-branch commits after the `ask` rule went. `soft_deny` now names only history on the protected branches and pushes, and `autoMode.allow` (which must keep `"$defaults"`, or it replaces the built-in exceptions) states the standing commit permission and that `/codex-review`'s `codex exec` runs inside the sandbox — without that entry the classifier refuses it as `[Create Unsafe Agents]`, approvals being off. The exact entries are in plan 0018.
- `permissions.ask` also covers `git checkout *`, but it does not guard the hazard it was added for. Switching branches in the deployed clone silently swaps the live global config (ADR 0001), and sessions here switch with `git switch`, which the rule does not match: this repository's session transcripts hold 18 `git switch` branch switches against 2 `git checkout` ones (2026-06-13 to 2026-10-26). Since the git gate hook went (plan 0025), the rule is the only prompt for any `checkout` form, `git checkout -- <path>` included, which discards working-tree changes. A global `Bash(git switch *)` ask would prompt in every repository.
- Mutating `git -C <other-repo> …` forms are denied while the read-only ones are allowed — a blanket `Bash(git -C *)` deny breaks `/adopt-from-sibling`, whose whole job is reading a neighbouring checkout.
- **Anchor every `Bash(…)` pattern at the command name; never lead with `*`.** Patterns are matched against the whole command string, not the program being run, so `Bash(*deploy*)` matched the word *inside a PR body* and refused to open the PR — and would equally refuse `sed -n 1p docs/deployment.md`. Anchored entries (`Bash(wrangler deploy*)`) deny the real thing while leaving the word harmless in arguments, paths and message text. This is the same reasoning that makes the `git -C` rules above name a verb rather than sit on a prefix.
- **Deny a destructive subcommand whole, not one spelling of its flags.** `Bash(git clean -f *)` matched `git clean -f` and `git clean -f x` but not `git clean -fd` or `-xfd`: a rule matches the text before its `*` literally, and combined short flags put other letters after `-f`. Measured on 2026-10-26, `git clean -fdn` (a dry run, so harmless either way) ran under that entry and is refused under `Bash(git clean *)`, which replaced it. Until then only the auto-mode classifier stood between a session and `git clean -fdx`, and in Manual mode nothing did. The wider entry also refuses `git clean -n`, which no session had run since the transcripts begin on 2026-06-13; `git status --ignored` and `git ls-files --others` list the same files. It still misses `bash -c 'git clean …'`, since a pattern matches only the command text, and `git -c k=v clean …` only asks, through `Bash(git -c *)`. For those, the classifier's `Irreversible Local Destruction` rule, which names `git clean -fd[x]`, is what remains.
- **Anchor `Read(…)` patterns too — at a filename or an extension, never a bare word.** The rule above was written for `Bash(…)` and its absence here cost a second time: `Read(**/*token*)` matches **480 paths** under `~/Developer`, and every sampled one was a lexer, a tokenizer or a document rather than a credential — `js-tokens`, `postcss/lib/tokenize.js`, `@csstools/css-tokenizer`, two tokenizer exercises. (Name matches, not 480 enforced denials: reads of them succeed today because they sit outside the working directory the unanchored `**/…` forms resolve against.) "Token" means a lexical token and a design token far more often than an auth token, and a substring cannot tell them apart. Worse than noise: these denies are merged into the sandbox, so with the working directory inside a JS project the pattern covers the `node_modules/js-tokens/` **directory** — a Babel dependency — and a build can fail on a permission error nobody would trace to a permission rule. (That last step is inferred from the merge behaviour plus the working-directory scope finding, not measured: the decoy needed to prove it could not be written inside this repo.) `Read(**/*.token)` names an artifact instead of a word. Accept that it catches little — almost no credential file is *named* "token" — and do not read that as "everything else is covered": the next bullet names token-bearing files this configuration deliberately leaves readable.
- **Do not deny a credential belonging to a tool you actually run sandboxed.** `.npmrc` and `~/.codex/auth.json` look like obvious `credentials.files` additions. They are not: `npm` and `codex` are themselves sandboxed commands, so such a rule withholds the secret from your own tool rather than from an attacker — `~/.codex/auth.json` was added, did exactly that, and had to be reverted. This is *not* an argument against the `~/.ssh`, `~/.aws` and `~/.config/gcloud` denies above: those are deliberate and they work precisely because nothing run from here is meant to authenticate with them. The test is not "is this a credential" but "does a command I run *inside the sandbox* need to read it". `gh` is the instructive counter-case: the user's login stays in the denied keychain, so `gh` runs outside the sandbox with it. Where a project runs `gh` sandboxed, it reads a narrow token of that project's own, which must stay readable (the per-project token bullet below). For tokens that arrive through the environment instead of a file, the matching mechanism is `sandbox.credentials.envVars` — `{"name": "GITHUB_TOKEN", "mode": "deny"}` unsets them before each sandboxed command, and unlike the file rules it holds even if filesystem isolation is turned off.
- **`credentials.files` denies `~/Library/Keychains` — keep it, it is what makes the two denies above mean anything on macOS.** Claude Code stores its own login there, not in `~/.claude/.credentials.json`. It reads it with `security find-generic-password -s "Claude Code-credentials" -w`, and `gh` and git's `osxkeychain` helper keep their GitHub credentials in the same `login.keychain-db`. Without this entry, any sandboxed command could read all three: measured on 2026-10-03, the Claude login came back as 523 characters, the `gh` token as 40, and git's credential as 114 bytes, even though `GITHUB_TOKEN` and `.credentials.json` were both denied. With it, all three come back empty, while `curl` TLS and public `git ls-remote` still work. It is the deliberate exception to the bullet above: git over HTTPS uses this keychain and is a sandboxed tool, so a `git push`, or a fetch from a private repository, can no longer authenticate inside the sandbox and has to run outside it. That costs one prompt per push. Leaving the entry out would expose every credential in the login keychain. Evidence: [`plans/0016-gh-sandbox-tls.md`](plans/0016-gh-sandbox-tls.md).
- **No `SSL_CERT_FILE` in `env` here, and `enableWeakerNetworkIsolation` stays off.** The variable lets Go programs such as `gh` verify TLS inside the sandbox without trustd (§ Git in this clone needs the sandbox turned off). A settings `env` reaches unsandboxed commands too (measured on 2026-10-28). So wherever it is set, every program that honours it uses `/etc/ssl/cert.pem` instead of the macOS trust store, inside the sandbox or not:
  - a root trusted only in the keychain is refused;
  - Go skips the platform verifier's checks, revocation included.

  Only a project with a `gh` token of its own gains anything from it, so it goes in that project's settings, beside the token (next bullet). The tools measured with it set, inside the sandbox, on 2026-10-28:
  - `curl` to `api.github.com`: 200;
  - `git ls-remote` over HTTPS: works;
  - Python 3.14's `urllib`: 200;
  - `uv` 0.13.4 resolved a package.
- **`gh` tokens live under `~/.config/gh-tokens/`, which `sandbox.filesystem.denyRead` denies; never put one in `~/.config/gh`.** A project that runs `gh` sandboxed opts in with its own `.claude/settings.local.json`:
  - `env.GH_CONFIG_DIR`, naming one folder under `~/.config/gh-tokens/`;
  - `env.SSL_CERT_FILE=/etc/ssl/cert.pem`;
  - `sandbox.filesystem.allowRead` holding that same folder.

  The folder holds a fine-grained token in plain text.
  - **Keep the user-level deny, and its two permission rules.** `sandbox.filesystem.denyRead` holds `~/.config/gh-tokens`, and `permissions.deny` holds `Read(~/.config/gh-tokens/**)` and `Edit(~/.config/gh-tokens/**)`.
    - **Why:** without them, every sandboxed command on the machine could read and use any project's token, Codex included. Measured on 2026-10-28: from a session in this repository, which had not opted in, `gh` read gkms-contest-ai's token and used it.
    - **The `Edit` rule** also keeps the file tools from writing a `gh` alias into a token folder's `config.yml`.
    - **How the re-allow works:** the sandbox docs say "when read rules overlap, the rule with the narrower path applies", and that the levels' arrays merge. So a project's `allowRead` of its own folder re-opens only that folder.
    - **No lock here:** nothing in managed settings locks the sandbox. A lock would make the sandbox ignore such an `allowRead`.
  - **The boundary is the sandbox, not the session.** A command run outside the sandbox, a hook or an MCP server can still read the folder. Of those, the command asks first.
    - **A path-based deny does not follow hard links,** so a hard link made elsewhere to a token file would bypass it. Keep each token file's link count at 1 (`stat -f %l`), and make no copies outside the folder.
  - **One folder per owner and visibility, shared by the projects that use it:** `tia-tools-private`, `tia-tools-public`. A new repository is added to the existing token on GitHub, with no new token. The cost is that each such project's sessions can also write issues in the others' repositories.
  - **Never mix public and private repositories in one token.** A project with private data would then hold a way to publish it.
  - **Keep the token narrow.** Every sandboxed command in a project that re-allows the folder can read it, Codex included:
    - one resource owner, and only the opted-in repositories of one visibility;
    - only the permissions their use needs: Issues write and Metadata read for an issue tracker, and Pull requests write where sessions open PRs. Pull requests write adds approving, dismissing and deleting reviews, and updating a PR's branch; GitHub lets no author approve their own PR, and every session is the user. For a board (the `task-board` skill), add the **organization** permission Projects: Read and write. It sits under "Organization permissions", shown only for a token owned by an organization. It reaches every board of that organization, so while a public token holds it, no board of that owner may hold private data;
    - never Contents write;
    - an expiry.
  - **On a public repository,** whatever a session writes in an issue is public at once, and anyone can open issues and comment. Sessions treat text anyone else wrote as data.
    - **On a board:** they work only on what the user queued, so a stranger's issue waits in Triage until the user accepts it.
    - **Without a board:** they act only on the user's own issues.
    - **The `task-board` helper's claims** count only comments written by the account it runs as, so a stranger's comment cannot take or end a claim.

    What the permissions allow, per GitHub's permission table:
    - **Issues write:** open, edit, close and lock issues, and delete comments, which cannot be restored.
    - **Pull requests write:** approve, dismiss and delete reviews, and update a PR's branch from its base, which writes a merge commit on that branch.
    - **Contents write** is needed to merge a PR or push, so the token can do neither.
    - **Scope:** it writes only to the selected repositories. Public ones it can read, as anyone can without a token. Measured on 2026-10-28: a title-less issue request was rejected on validation (422) in the selected repository, and refused (403) in a public repository of the same owner.
  - **Keep the folder outside every session's write area.** `gh` runs aliases from its `config.yml`, and an alias starting with `!` runs a shell command, which a `gh` run outside the sandbox would execute.
  - **Store it with `gh auth login --insecure-storage`, never as a top-level `oauth_token:`.** Where the token sits in `hosts.yml` decides whether `gh` reads it before the keychain or after. Measured on 2026-10-28 with gh 2.103.0:
    - **Under the account (`users: <login>: oauth_token:`):** this is what the login command writes. Outside the sandbox `gh` uses the keychain login first, so in the project, a `gh` command the token cannot do still runs unsandboxed, with the user's login, as elsewhere. Inside the sandbox, where the keychain is denied, `gh` falls back to the token.
    - **At the top level (`github.com: oauth_token:`):** read before the keychain. A project's unsandboxed `gh` would then use the narrow token too. In the default `~/.config/gh` it would replace the user's login in every `gh` call in every project.

    The project's `GH_CONFIG_DIR` reaches unsandboxed commands too, since a settings `env` does.

  Evidence: [`plans/0027-gh-sandboxed-per-project.md`](plans/0027-gh-sandboxed-per-project.md) and [`plans/0029-gh-token-read-isolation.md`](plans/0029-gh-token-read-isolation.md).
- Hook commands must be self-contained and portable. They run under `sh -c` on macOS/Linux and Git Bash on Windows, so a bare `afplay …` raises a non-blocking hook error on every Windows notification; branch on `uname -s` inline and end with `exit 0`.
- **Secrets are protected by the sandbox, not by `Bash(...)` command-pattern denies.** `sandbox.credentials.files` and `sandbox.filesystem.denyRead` are enforced by the OS for every Bash command *and its child processes*, so they bind `sed`, `awk`, `python3`, `rg` and everything else at once. A `Bash(...)` denylist can only ever match command strings, which is why the previous `cat`/`head`/`tail` bans were removed: they implied a protection they could not deliver, while `sed -n p` walked straight past them. Verified by decoy, not by reading a real secret — see the note below.
- **No `Bash(curl:*)` in `permissions.ask` — network access is limited by the sandbox, not by command name.** The entry was removed on 2026-10-04, and nothing recorded why it had been added. It was the same mistake as the `cat` bans: `wget`, `python3 -c`, `node -e` and `git` all reach the network without matching it. Meanwhile ask rules override auto mode, so it made *every* `curl` ask for approval. That included the unauthenticated GitHub API reads the global `CLAUDE.md` § Git Operations sends sessions to instead of `gh`, so each PR lookup cost a prompt. What actually limits `curl` is that sandboxed traffic can only reach `sandbox.network.allowedDomains`, and the `~/Library/Keychains` deny keeps tokens out of reach (bullet above). Leaving the sandbox still asks, because `Bash(dangerouslyDisableSandbox:true)` stays in `permissions.ask`. Do not try to replace the entry with a narrower allow such as `Bash(curl -s https://api.github.com/*)`: ask beats allow, so the broad ask rule would win regardless.
- **No `Bash(mv *)` in `permissions.ask` — where a move can reach is limited by the sandbox, and whether it destroys a file is judged by auto mode.** The entry was removed on 2026-10-26, and as with `curl`, nothing recorded why it had been added. The session transcripts on this machine hold 88 `mv` calls from 2026-06-13 to 2026-10-26. 87 ran sandboxed, so the OS already held them to the working directory, `$TMPDIR` and `sandbox.filesystem.allowWrite`. The one that reached another checkout ran unsandboxed, where `Bash(dangerouslyDisableSandbox:true)` asks anyway. The rule missed every other spelling (`/bin/mv`, `bash -c 'mv …'`, `python3 -c 'os.rename(…)'`), and `cp`, `>`, `tee` and `sed -i` overwrite a file just as `mv` does without asking. Worse, an ask rule resolves before the auto-mode classifier sees the command, and the classifier carries the rule that fits. Its default `Irreversible Local Destruction` soft-deny, kept by `"$defaults"` in `autoMode.soft_deny`, names "`mv`/`cp` … onto an existing untracked or out-of-repo path — without explicit user direction" and adds "Overwriting files the agent created this session is fine". Its `Local Operations` allow covers ordinary moves inside the project; `claude auto-mode defaults` prints both. The classifier does review sandboxed commands here: the same transcripts hold six sandboxed commands it denied between 2026-09-30 and 2026-10-14. What this leaves open, knowingly:
  - the classifier judges rather than matches: one of those six was a bare `date -u`, denied as `[Irreversible Local Destruction]`;
  - it judges only in auto mode. In Manual mode `sandbox.autoAllowBashIfSandboxed` (default `true`) runs a sandboxed `mv` with no prompt at all, so re-check this bullet if Manual mode becomes routine;
  - "inside the sandbox" is wider than the repository a session works in: `allowWrite` opens `~/Developer/claude`, `~/.codex` and `~/Movies/explainers` to every session;
  - `/rewind` restores only edits made with the file tools, never a Bash `mv`.

  If overwrites ever need a deterministic check, use a PreToolUse hook that asks only when a destination exists and is untracked or modified, not a narrower pattern, deployed as a copy no session can write (`docs/claude-code.md` § Code that runs outside the sandbox). Patterns that constrain arguments miss `-t DIR`, `$VAR` and `a/../../x`, and since ask beats allow, no `Bash(mv ./*)` allow can carve the in-repository case out of a broad ask rule. A hook's `allow` cannot override an ask rule either, so such a hook needs this entry to stay gone.
- **`Bash(rm *)` stays in `permissions.ask`, temp cleanup included — `$TMPDIR` is not a session's own scratch space.** Most of its prompts are cleanup: of the 267 `rm` calls in the session transcripts on this machine (2026-06-13 to 2026-10-26), 170 named their target through `$TMPDIR` or a variable set to a temp path in the same command. Exempting those was weighed on 2026-10-26 and rejected:
  - the same text names two directories. A sandboxed command gets `TMPDIR=/tmp/claude-501`; an unsandboxed one inherits the login shell's `/var/folders/…/T/`, as the transcripts show (`cat: /var/folders/mp/…/T//survey.txt`). So one command deletes different files depending on `dangerouslyDisableSandbox`;
  - `/tmp/claude-501` is one directory per user, shared by every session of every project. Measured on 2026-10-26 it held 930 entries and 15 GB, among them 249 git checkouts and 184 `/codex-review` snapshots. The auto-mode classifier's default `Shared Scratch Sweep` rule warns that these directories "are shared with other agents and processes";
  - nothing empties it. macOS 26.7.1 has no `/etc/periodic`, the oldest entry dates from 2026-09-29, and `/codex-review` creates its snapshot with `mktemp -d "$TMPDIR/codex-review.XXXXXX"` and never removes it;
  - a command can only prove a path is its own when it creates it, because shell variables do not survive between Bash calls, and the usual pattern creates a directory in one call and removes it in a later one;
  - a hook's `allow` cannot override this rule, so any carve-out means deleting the rule and moving all of `rm`'s asking into a hook, and a hook that crashes counts as no decision.

  Existing guards split on exactly this. [cc-safety-net](https://github.com/kenryu42/cc-safety-net) trusts every temp root, and its test fixtures allow `rm -rf $TMPDIR` itself. [dcg](https://github.com/Dicklesworthstone/destructive_command_guard) trusts a `$TMPDIR` path only when the same command assigns it, and its [issue #590](https://github.com/Dicklesworthstone/destructive_command_guard/issues/590), open on 2026-10-26, reports Claude Code's `claude-<uid>` roots as unrecognised. If the prompts ever need cutting, the shape that answers all five points is a per-session root (`$TMPDIR/<session id>/`) plus a dedicated delete command. It would resolve its targets with `realpath` at run time, refuse anything outside that root, and get an allow rule of its own while `Bash(rm *)` stays. It is not built or tested, and it helps only once sessions, `/codex-review` among them, put their scratch files there.
- `Read(…)` denies for secret paths stay, but not for the reason once written here. They are **merged into the sandbox**: per the [sandboxing docs](https://code.claude.com/docs/en/sandboxing), paths from permission rules and from sandbox settings are combined into the final sandbox configuration, and this machine's resolved config contains `id_rsa`, `**/*token*`, `**/build` and `./.dev.vars` — entries present nowhere in the `sandbox` block. So they bind Bash too. What keeps both lists earning their place is *scope*: a `.key` file created under `$TMPDIR` was readable, so the unanchored `**/*.key` form does not cover the machine, while the `~/**/*.key` entries in `sandbox.filesystem.denyRead` do.
- `grep`/`find` remain denied as a *tooling* preference — the dedicated Grep and Glob tools are better — and should be understood as a nudge, not a control. Note the tier is disproportionate for a preference; `ask` would be the honest setting if the nudge ever becomes annoying.
- `permissions.ask` carries `Bash(dangerouslyDisableSandbox:true)`. A command the sandbox blocks can be retried outside it, and without that rule the retry is judged by the auto-mode classifier rather than by you. `sandbox.allowUnsandboxedCommands: false` closes the hatch entirely, at the cost of breaking anything genuinely un-sandboxable until it is listed in `excludedCommands`.
- **Running Codex inside the sandbox takes two entries, and forbids a third.** `sandbox.network.allowedDomains` needs `chatgpt.com` and `auth.openai.com` (a ChatGPT-plan login; `api.openai.com` under API-key auth), and `sandbox.filesystem.allowWrite` needs `~/.codex` — without which Codex dies at startup on `could not create PATH aliases` / `failed to initialize in-process app-server client`, a filesystem failure that looks nothing like a blocked host. Do **not** put `~/.codex/auth.json` in `credentials.files`: that rule protects a credential *from* sandboxed commands, and Codex is one, so it leaves Codex unable to authenticate. Codex's own sandbox must also be off (`--sandbox danger-full-access`) — Seatbelt does not nest, so its `read-only` mode fails every command it runs with `sandbox-exec: sandbox_apply: Operation not permitted`. Buying this costs egress width and buys `denyRead` binding the process most likely to wander the filesystem — see [`plans/0008-codex-read-boundary.md`](plans/0008-codex-read-boundary.md).
- **Test host reachability with a proxy-aware client.** The sandbox routes permitted traffic through a local filtering proxy given in `HTTP_PROXY`/`HTTPS_PROXY`; Node's built-in `fetch` ignores those and reports `ENOTFOUND` for allowed hosts as readily as blocked ones. `curl` honours them — measured, `node` said `ENOTFOUND` for `api.github.com` while `curl` got `200` from it. A negative result from a proxy-blind tool is not evidence, and it reads as conclusive because it is specific.
- **The sandbox does not run on native Windows** (macOS, Linux and WSL2 only). On such a machine the layer above simply is not there, and the pattern denies become the only shell-side control — so re-add `cat`/`head`/`tail` there rather than assuming this file is portable.
- JSON admits no comments, so any non-obvious entry needs its reason recorded here rather than in the file. When testing whether a read rule works, use a **decoy** file with harmless contents: verifying against a real key means that if the rule is *not* enforcing, the test prints key material into the transcript — the exact outcome being tested for.

## Changing the harness

1. Feature branch, following `CLAUDE.md` § Git Operations (yes, this repo obeys its own rules).
2. Non-trivial change → add a short plan file in `plans/` (goal, changes, verification — ~40 lines, isamu-style).
3. Harness-architecture decision that passes the three-gate test (hard to reverse, surprising without context, real trade-off) → ADR in `docs/adr/`. Expected to stay in the low single digits; most changes need none.
4. PR to `master` with the rationale in the description. Merge = deploy.

## Relationship to project-template

`Taka499/project-template` remains the per-project scaffold: `docs/adr/README.md` (ADR convention), `docs/plans/`, and the `CLAUDE.md` skeleton that new projects copy. Everything reusable across projects — rules, skills, stack notes — lives here instead and reaches projects through `~/.claude`.

The ExecPlan methodology is the one document both repos need. `docs/PLANS.md` here is the **canonical** copy: global `CLAUDE.md` mandates ExecPlans, so the definition has to be readable from any project, including one with no scaffold checked in. project-template still ships a copy — a plan must be followable from a fresh clone with no `~/.claude` — but that copy is a downstream sync target, not an independent document. When this file changes, propagating it to project-template is the follow-up PR.
