# Claude Code — distilled cross-project lessons

Lessons about Claude Code itself: its sandbox, permission rules, hooks, and sessions in git worktrees, independent of the project's language. The git rules under the sandbox stay in the global `CLAUDE.md` § Git Operations. Read this note before writing hooks, permission rules or sandbox settings for a project, and before running several sessions in worktrees of one repository.

## Code that runs outside the sandbox

**Anything that runs outside the sandbox without a prompt must be a copy no session can edit, and a hook should only read.** Command hooks always run outside the sandbox with your full access, and so does every command matched by `sandbox.excludedCommands`. If such a command runs a script that a sandboxed session can write, the session can change the script, and the next run executes the change unsandboxed and unprompted, which is what the sandbox exists to prevent. Point every hook and exclusion at an absolute path that no session's sandbox can write: outside every directory a session is given, or covered by an `Edit(//absolute/path/**)` deny rule, which Claude Code merges into the sandbox's restrictions, so it stops sandboxed Bash as well as the Edit tool. The script then changes only through a reviewed merge. Keep hook scripts read-only, so a wrong hook blocks or misreports but damages nothing, and pin that with a test that fails when a hook script opens a file for writing. (gkms-contest-ai, 2026-10-14: hooks registered in the tracked `.claude/settings.json` ran each worktree's own, session-editable copy of their scripts outside the sandbox for about 21 h before it was found.)

**A Python hook imports from its own directory before the standard library, so protect the directory, not only the file, and run the interpreter with `-I`.** `python3 /path/hook.py` puts `/path` first on the import path, so a `json.py` written beside the hook runs in place of the standard library's as soon as the hook imports `json`; the hook file itself never changes. `-I` (isolated mode) leaves the script's directory off the import path and ignores the `PYTHON*` environment variables and the user's site-packages. (Measured 2026-10-28 with Python 3.14.9: a planted `json.py` beside a script ran, and with `-I` it did not. This harness's own git hook ran without `-I` from a directory every session could write; `plans/0025-remove-git-gate.md`.)

**In a worktree session, tracked settings come from the worktree and local settings from the main checkout.** Claude Code loads `.claude/settings.json`, hooks included, from the session's working directory with no fallback to a parent, so a worktree session uses the worktree's copy of that file, and a hook that names its script relative to the project runs the worktree's copy of the script. Since v2.1.211, `.claude/settings.local.json` loads from the git repository root, resolved through worktrees to the main checkout (not on Windows, outside a git repository, or in Agent SDK sessions), so a hook or rule registered there reaches every worktree session of the repository. Its path rules still anchor at each session's own working directory. That file is untracked and machine-local. For a repository worked on from several worktrees, register hooks there with absolute paths to the main checkout's copies. That meets the rule above only together with a deny rule on those copies: a session working in the main checkout, or one whose sandbox `allowWrite` reaches it, can otherwise write them. (Claude Code docs, permissions page, read 2026-10-26; gkms-contest-ai, 2026-10-23, Claude Code 2.1.308: a worktree session ran a SessionStart hook registered only in the main checkout's local settings.)

## A hook that cannot run

**A guarding hook that cannot start or crashes fails open, and one whose script file is missing blocks everything; name the interpreter by a path that survives upgrades, and guard the script's existence.** Claude Code treats a hook that exits with any code but 0 or 2 as a non-blocking error, so the tool call goes ahead with no decision from the hook. A hook that runs a Python script fails that way when its interpreter is gone or too old:
- A bare `python3` can resolve to Apple's `/usr/bin/python3`, 3.9.6 when measured on 2026-10-28, which cannot import code using newer syntax.
- Homebrew's `/opt/homebrew/bin/python3` belongs to its default Python and disappears when the default moves to a new version.

Name the version's own link, `/opt/homebrew/opt/python@3.X/libexec/bin/python3`: it follows that version's patch upgrades and survives `brew cleanup`. Move the entry when that version is retired.

The opposite failure is worse. Python exits 2 when its script file is missing, and exit 2 from a PreToolUse hook blocks the call. A checkout or a deletion that removes the script would then refuse every Bash command in every session, including the ones needed to repair it. Run the script only if it exists, and exit 1 otherwise: `f=/path/hook.py; if [ -f "$f" ]; then /opt/homebrew/opt/python@3.X/libexec/bin/python3 -I "$f"; else echo "hook.py not found at $f" >&2; exit 1; fi`.

(This harness, 2026-10-22: a Homebrew upgrade moved the default Python to 3.15 and removed `/opt/homebrew/bin/python3`, and the git hook failed open on every Bash call until its entry was changed; `plans/0023-gate-interpreter-path.md`. Exit 2 for a missing script measured 2026-10-28 with Python 3.14.9, with and without `-I`.)

## Permission rules

**Approve a script with an exact-path allow rule and let the script check its own arguments; never grant a command by parsing its shell text.** How Claude Code matches Bash rules:
- It splits a compound command on `&&`, `||`, `;`, `|`, `|&`, `&` and newlines, and an allow rule must match every part on its own.
- Before matching, it strips the wrappers `timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin` and zsh's `noglob`, plus a leading assignment of certain known-safe variables. An allow rule does not match past any other assignment, and runners such as `env`, `npx` or `direnv exec` are not stripped.
- Deny and ask rules also match inside subshells, command substitutions and loop bodies. Whether an allow rule matches past a `$(…)` inside a command's arguments is not documented.

A hook that parses the command text to *grant* a command inherits every gap in its parser. In one project that was measured: false prompts, then security findings, then hardening. Instead, give the script an exact-path allow rule, plus its `sandbox.excludedCommands` entry if it must run outside the sandbox. The script validates its arguments and resets its own environment (`env -i` with a fixed `PATH`) at its first line. Before relying on such a rule for an excluded command, measure in a session in the default permission mode whether a `$(…)` in its arguments prompts: under the exclusion, that substitution would run unsandboxed. Keep text parsing to hooks that can only *ask*, failing toward a prompt, and count what such a hook costs before keeping it. This harness removed its own on 2026-10-28, a hook asking before git history reached protected branches: it prompted about 225 times in 16 days, about 164 of them for commands it could not read, and it ran from a file every session could write (`plans/0025-remove-git-gate.md`). (gkms-contest-ai, 2026-10-23; Claude Code docs, permissions page § Compound commands and § Wrappers, read 2026-10-26.)

## Processes under the sandbox

**List your own jobs with `lsof -d cwd | grep "$PWD"`, not `ps` or `pgrep`.** Inside the sandbox `ps` fails with `operation not permitted` and `pgrep` with `Cannot get process list`; run outside it, each one is a permission prompt. `lsof -d cwd` lists every process whose working directory is under the project and works sandboxed: your servers, test runs and long jobs, plus the session's own `claude` and helper processes. (gkms-contest-ai, 2026-10-15: 18 prompts came from `ps` and `pgrep` after a written note against them; measured again 2026-10-26, Claude Code 2.1.310.)
